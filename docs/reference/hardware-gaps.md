### `catsniffer-v3`

Electronic Cats CatSniffer v3 — multiprotocol sub-GHz, BLE and 802.15.4

No USB identifier confirmed. CatSniffer v3 combines a TI radio with a host-side USB serial interface; whether that is a native CDC endpoint or a bridge chip has not been verified against hardware here, and no distribution ships a udev rule naming it. The badgelife class rules cover CP210x, CH34x and ESP32 native USB, which is likely to include it, so the device works without a pinned identifier. Run lsusb with it attached and add the confirmed pair before this entry claims status: supported.

### `clip-boy`

Open-source DEF CON badge — ESP32-S3 with an LVGL touch UI

No USB identifier confirmed. Clip-Boy is an ESP32-S3 design, so it most likely enumerates on Espressif's native USB CDC — which the badgelife class carries as 303a:1001, itself marked unconfirmed. Whether this board exposes native USB or routes through a bridge chip has not been verified against hardware. The class rules cover every plausible case, so the device works without pinning an ID; this entry does not guess one.

### `esp32-marauder`

justcallmekoko's ESP32 Marauder — 2.4 GHz Wi-Fi and Bluetooth survey firmware on ESP32 hardware

Per-revision, and deliberately not narrowed further than the evidence allows. Marauder is a firmware that runs on several hardware builds, and the USB path differs between them: older boards use a CP2102 bridge (10c4:ea60) or a CH340 (1a86:7523), both already confirmed in the badgelife class from Debian's usb.ids; ESP32-S3-based boards present Espressif's native USB CDC under vendor 303a, which the class carries as unconfirmed. So the entry does NOT assume a bridge — it inherits all of them from the class, which is why the device works today without a pinned identifier. What is unknown is which one THIS board uses, and the answer also settles the class's unconfirmed 303a entry if it turns out to be an S3. The board revision is likewise unconfirmed and must be read off the silkscreen rather than assumed.

### `meshtastic`

Meshtastic LoRa nodes — T-Deck, T-Echo, RAK and WisMesh boards

Not a single device and deliberately not treated as one. ### `proxmark3`

## Support and verification are two different claims

`status` says the identifiers and setup recipe are correct. `maintainer_verified` says somebody here plugged the hardware in. They answer different questions, and a device can honestly be the first without the second: `usrp` claims `supported` on the strength of Debian's own `uhd-host` udev rule, a primary source, while nobody on this project owns one.

Discarding that evidence for lack of hardware would throw away a real claim. Merging the two columns is how a project comes to claim support it has never tested. So they are separate fields and both are shown.
