### `catsniffer-v3`

Electronic Cats CatSniffer v3 — multiprotocol sub-GHz, BLE and 802.15.4

No USB identifier confirmed. CatSniffer v3 combines a TI radio with a host-side USB serial interface; whether that is a native CDC endpoint or a bridge chip has not been verified against hardware here, and no distribution ships a udev rule naming it. The badgelife class rules cover CP210x, CH34x and ESP32 native USB, which is likely to include it, so the device works without a pinned identifier. Run lsusb with it attached and add the confirmed pair before this entry claims status: supported.

### `clip-boy`

Open-source DEF CON badge — ESP32-S3 with an LVGL touch UI

No USB identifier confirmed. Clip-Boy is an ESP32-S3 design, so it most likely enumerates on Espressif's native USB CDC — which the badgelife class carries as 303a:1001, itself marked unconfirmed. Whether this board exposes native USB or routes through a bridge chip has not been verified against hardware. The class rules cover every plausible case, so the device works without pinning an ID; this entry does not guess one.

### `free-wili-2`

### `meshtastic`

Meshtastic LoRa nodes — T-Deck, T-Echo, RAK and WisMesh boards

Not a single device and deliberately not treated as one. Meshtastic runs on many boards using at least three different USB paths: ESP32-S3 native USB (T-Deck), nRF52840 with an Adafruit-style bootloader (T-Echo), and CP210x or CH34x bridges on older or cheaper boards. Only the CP210x and CH340 identifiers in the badgelife class are confirmed here. The nRF52840 boards enumerate differently again in bootloader mode. Record lsusb per board rather than assuming.

### `minino`

Electronic Cats Minino — 802.15.4 and Zigbee analysis board

No USB identifier confirmed. Minino is an ESP32-based board, so the badgelife class rules most likely cover it via native USB CDC or a bridge chip, but this has not been verified against hardware and no distribution ships a rule naming it. Confirm with lsusb before claiming support.

### `proxmark3`

Proxmark3 — RFID and NFC research tool (original design; RDV boards unverified)

No USB identifier confirmed yet, but the hardware to confirm one is in the maintainer's kit and simply has to be located — this is a deferred task, not a contribution ask. The unit is an original-design Proxmark3, not an RDV4 or RDV5. That matters: the identifier differs across generations and across Iceman-firmware variants, which is exactly the situation where a guessed VID:PID produces a udev rule that silently never matches. So the lsusb capture will close this entry for the original design only; the RDV boards stay unconfirmed and need their own evidence from someone who owns one. No Debian package ships a Proxmark udev rule to read an identifier from, and the client is not packaged. The bootloader enumerates separately and needs its own record.

### `krakensdr`

KrakenSDR — five coherent RTL-SDR receivers for direction finding

Not separately identified. KrakenSDR is five RTL2832U receivers on one board, so each channel enumerates with the ordinary RTL-SDR identifiers already confirmed in the rtl-sdr entry (0bda:2838). What is NOT confirmed is whether the board exposes any additional control interface with its own identifier. The per-channel rules work regardless; only a board-level rule is unverified. The maintainer does not own one, so this needs lsusb output from an owner — a low-value gap, since the device is usable without it.

### `limesdr`
